# Scenario 5: Bob exceeds his access scope

Alice grants Bob write access to the "messages/" path only. Bob writes
within scope — succeeds. Bob tries to write outside scope — rejected.

---

## Setup (local — both nodes independently)

Same as [Scenario 1](01-happy-path-write-sync.md) Steps 1-3, except
Alice restricts Bob's delegation to a specific area:

```rust
let restricted_area = Area::new(
    AreaSubspace::Id(bob_id),       // Bob's subspace only
    Path::from_bytes(&[b"messages"]), // "messages/" prefix only
    Range::new(0, RangeEnd::Open),  // any time
);
auth.delegate_write_cap(&selector, bob_id, RestrictArea::Restrict(restricted_area))
```

> `src/store/auth.rs:254`

The delegation chain's leaf has `wil_*` policy predicates:
```
["==", ".wil_subspace", <bob_id bytes>]
["or", ["==", ".wil_path", "messages"], ["like", ".wil_path", "messages/*"]]
```

The path predicate uses `Or(Equal, Like)` — the `Equal` arm matches
the exact path, the `Like` arm with a glob matches any sub-path.
Generated by `area_to_predicates()` (`src/uwill/area_extract.rs:166`).

## Bob writes within scope — succeeds (local — Bob's node builds invocation)

Bob's node builds a write invocation locally at path `messages/hello`:

```
build_write_invocation(&entry, &chain, &bob_secret)
```

> `src/uwill/invocation.rs:148`

The invocation args describe the **capability's area** (not the entry):
`area_to_args(chain.granted_area())` produces `wil_subspace`,
`wil_path` fields from the chain's granted area.

> `src/uwill/area_extract.rs:223`

During `validate_write()` (`src/uwill/invocation.rs:282`), three
validation stages run (local on whichever node performs the check —
Bob's node for local writes, Alice's node when receiving entries
over the wire):

**Stage 1 — `validate_common()`** (line 283):
```
let chain = self.validate_common()?;
```
Runs shared stateless checks: invocation signature, chain integrity
via `from_chain()` (delegation signatures, root issuer, subject
consistency, area narrowing), and expiry. No revocation — that's
stateful, checked at security boundaries.

**Stage 2 — `run_syntatic_checks()`** (line 284):
```
self.run_syntatic_checks()?;
```
Calls the `ucan` crate's `syntatic_checks()` which validates:
- Subject matches namespace DID
- Issuer chain alignment
- Command hierarchy (`willow/write`)
- **Area predicate evaluation** — the invocation's args are checked
  against each delegation's `Or(Equal, Like)` path predicates and
  `Equal` subspace predicates

**Stage 3 — Willow-native checks** (lines 286-296):
```rust
if !chain.proves_write() { ... }
if chain.granted_namespace() != *entry.namespace_id() { ... }
if !chain.granted_area().includes_entry(entry) {
    return Err(InvocationError::EntryOutsideArea);
}
```

The root delegation has full area — includes everything.
The leaf delegation has area restricted to Bob's subspace + "messages/" path.
Entry is at `messages/hello` in Bob's subspace — included. All stages pass.

## Bob tries to write to "secrets/" — rejected

Bob's node builds an invocation locally for path `secrets/keys`, then
sends it over the wire. The validation failure happens on Alice's node
when she receives the entry.

Same flow. The invocation is built locally on Bob's node with the
capability's area args (which describe the "messages/" area).
`validate_common()` and `run_syntatic_checks()` pass because the chain
and args are internally consistent. But in stage 3 (on Alice's node,
validating received data):

```rust
let chain = self.validate_common()?;
// chain.granted_area() = {bob_subspace, "messages/", any time}
if !chain.granted_area().includes_entry(entry) {  // entry path is "secrets/keys"
    return Err(InvocationError::EntryOutsideArea);
}
```

> `src/uwill/invocation.rs:294-296`

`"secrets/keys"` is NOT a prefix extension of `"messages/"` —
`includes_entry` returns false — `EntryOutsideArea` error.

`is_authorised_write` (line 418) returns `false` — it's a
defense-in-depth wrapper that calls `validate_write(entry).is_ok()`.
The security boundary for entries received from peers is
`static_tokens.rs` (on the receiving node) + explicit revocation
check (against the receiving node's local store). The entry is not
ingested on Alice's node.

## Bob tries to write to Alice's subspace — rejected

Bob's node builds an invocation locally at path `messages/hello` but
in Alice's subspace, then sends it over the wire:

```rust
Entry::new(ns_id, alice_id.into(), ...)  // Alice's subspace, not Bob's
```

Same validation flow on the receiving node (Alice's node). The
delegation's area has `AreaSubspace::Id(bob_id)`. The entry's subspace
is `alice_id`. `chain.granted_area().includes_entry()` checks subspace
membership locally — Alice's subspace doesn't match —
`EntryOutsideArea`.

## How area narrowing is enforced

Delegation chain narrowing is verified at construction time in
`from_chain()` (`src/uwill/chain.rs:148`):

```rust
if !prev.includes_area(&area) {
    return Err(ChainError::AreaWidening { step: i });
}
```

> `src/uwill/chain.rs:201-202`

Each delegation's area must be a subset of the previous one. Bob
can't delegate wider access than he was granted — the chain
validation rejects it before it can be used.
